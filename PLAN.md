# wow3ds — план и состояние проекта (передача в новый чат)

Порт клиента WoW Vanilla 1.12.1 (build 5875) на New Nintendo 3DS с собственным рендером под PICA200.
Парсеры форматов берутся из MIT-проекта WoWee (https://github.com/Kelsidavis/WoWee).
Ассеты только из своего легального клиента 1.12. Игра на частном сервере без Warden.

**К новому чату приложить:** этот файл + `wow3ds-stage5z.zip` (весь код; ветка `claude/water` репозитория) + `w3dconv-win31.zip` +
результаты проверки (log_region.txt, placements.txt, preview/region.png, preview/coll_32_48.png, preview/creature_*.png, preview/player_*.png,
report.txt, фото/описание HUD с консоли, при сетевых вопросах — session.w3dl; с этапа 5.12 — survey_log.txt).

Железо: New 3DS, 2×ARM11 804 МГц (ядро 2 доступно приложению), ~124 МБ для приложения, VRAM 6 МБ,
PICA200, экраны 400×240 / 320×240. Тулчейн: devkitARM + libctru + citro3d (пользователь собирает сам через `make`;
у ассистента в песочнице сервер пакетов devkitPro закрыт — проверка идёт компиляцией под ARM11 + picasso.
В чате этапа 5 PyPI тоже был закрыт (zig не поставить) — работает системный clang 18 + заголовки libc++ из
llvm-project с GitHub, см. `tools/armcheck/README.md`; Windows-сборка w3dlogin.exe — llvm-mingw с релизов GitHub).

## Важные находки (не терять)

Железо/PICA:
- **Аппаратный туман PICA (LUT по глубине) на консоли работает неверно** — ближнее заливалось целиком.
  Туман считается в вертексном шейдере по расстоянию и смешивается отдельной TEV-ступенью (зелёный канал цвета вершины).
- **Кэш ядер ARM11 MPCore не когерентен для GPU**: после fread на ядре 2 сброс кэша делает само ядро
  (`svcFlushProcessDataCache` в потоке ввода), иначе GPU читает старые данные.
- Отсечение граней: земля CCW сверху → `GPU_CULL_BACK_CCW`; листва/альфа-ключ/полупрозрачное — без отсечения
  (в M2 часто нет флага двусторонности).
- Координаты: позиция с сервера == координаты рендера (WoWee core/coordinates.hpp); тайл: tileX = floor(32 − y/533.33),
  tileY = floor(32 − x/533.33). Uniform'ы PICA — float24, поэтому всё рисуется относительно камеры (модельвью на CPU в float32).
- libctru по умолчанию даёт linear heap только 32 МБ — в main.cpp `__ctru_heap_size = 24 МБ`, остальное (~90 МБ) — linear.
- Пул ячеек земли (36 слотов, ~0.7 МБ) — без фрагментации; модели/текстуры с подсчётом ссылок; освобождение через 2 кадра.
- Мипы листвы с сохранением покрытия альфы (иначе кроны «редеют» и мигают вдали).
- Командный буфер citro3d 2 МБ (при тысячах draw call 1 МБ на грани переполнения → svcBreak).
- Скиннинг: 96 vec4-униформ вершинного шейдера → палитра 24 кости × 3 строки (72) + 13 своих. Индекс кости в атрибуте
  уже ×3; одна `mova a0.xy` на обе кости (две `mova` подряд вешают PICA), между `mova` и первым `bones[a0.x]` — другие
  инструкции. Относительная адресация — только SRC1 (униформа первым операндом `dp4`).
- Формула костей (WoWee computeBoneMatrices): M = M_parent · T(pivot) · T(t) · R(q) · S(s) · T(−pivot); индексы костей
  вершин — глобальные; ванильные треки — диапазоны на последовательность, время от начала диапазона.

Протокол 1.12.1 (build 5875):
- Auth protocol 3 (как оригинал; vMaNGOS принимает и 8). Ответ на proof — 26 байт. Список реалмов — ванильный формат
  (u32 icon, u8 count). CRC-хэш клиента — нули (серверы по умолчанию не проверяют).
- Мир: заголовок SMSG = u16 size BE + u16 opcode; CMSG = u16 size BE + u32 opcode; шифруются только заголовки
  (4/6 байт) сырым 40-байтным K, начиная сразу после CMSG_AUTH_SESSION. Аддоны — стандартные 12 Blizzard_*, zlib.
- Опкоды брать из WoWee `Data/expansions/classic/opcodes.json`, поля объектов — `update_fields.json`, НО сверять с
  vMaNGOS `src/game/Server/Protocol/Opcodes_1_12_1.h` и `src/game/Objects/UpdateFields_1_12_1.h` (git clone
  github.com/vmangos/core работает): у WoWee неверны PLAYER_BYTES (191/192 → на деле 193/194, перед ними GUILDID и
  GUILDRANK) и ITEM_FIELD_DURABILITY (48/49 → 46/47). В stage5q все 85 опкодов кода сверены автоматически.
- Warden определяется (SMSG_WARDEN_DATA 0x2E6), не отвечаем. На Stone Tavern Warden нет.
- Этап 5 (по WoWee packet_parsers_classic/tbc + vMaNGOS):
  UPDATE_OBJECT: u32 count, **u8 hasTransport**, блоки; MOVEMENT-блок — полный u64 GUID, остальные — packed.
  UpdateFlags 1.12 (u8): SELF 1, TRANSPORT 2, MELEE_ATTACKING 4, HIGHGUID 8, ALL 0x10, LIVING 0x20, HAS_POSITION 0x40
  (не совпадают с TBC/WotLK!). LIVING: MovementInfo + 6 скоростей (walk, run, runBack, swim, swimBack, turn), без pitchRate;
  при SPLINE_ENABLED (0x400000) — сплайн: flags, [FINAL_POINT 0x10000 / TARGET 0x20000 / ANGLE 0x40000], passed, dur, id,
  count, точки, end. Флаги движения 1.12: ROOT 0x1000, JUMPING 0x2000, SWIMMING 0x200000, ONTRANSPORT 0x2000000.
  Клиентские MSG_MOVE_* — без GUID; ретранслируемые сервером — packed GUID + MovementInfo.
  MONSTER_MOVE: packed guid, start xyz, u32 id, u8 тип (0 обычный, 1 стоп, 2 точка, 3 цель, 4 угол), flags, dur, count;
  линейный путь = dest + (count−1) упакованных смещений от середины (11/11/10 бит, ×0.25); Catmull-Rom/полёт — count
  точек целиком. Какой вариант — надёжнее всего по оставшемуся размеру пакета (флаги отличаются между ядрами).
  Сжатые пакеты: u32 исходный размер + zlib. ACK форс-изменений: u64 guid, counter, MovementInfo (+ float скорость);
  TELEPORT_ACK от клиента: u64 guid, counter, u32 time. GUID в SMSG_FORCE_* — packed (vMaNGOS), длину проверяем по размеру.
  Прыжок клиента: zspeed −7.9555, гравитация 19.29.

Проверка без консоли (повторять для нового кода):
- ARM11-компиляция: zig c++ `-target arm-freestanding-eabihf -mcpu=mpcore` + заголовки libctru/citro3d/newlib devkitPro
  (рецепт и флаги — `tools/armcheck/` в архиве).
- Шейдеры: picasso, собранный из исходников devkitPro.
- Логика стриминга: streamer.cpp с заглушками libctru под ASan/TSan (5×5 тайлов, без ошибок и утечек).
- Сеть: SRP 300/300 совпадений с WoWee/OpenSSL; полный вход против fake_server.py; затем реальный сервер.
- Этап 5: `net/tests/run_stage5.sh` (objects_test 29/29 + фаззинг 42 000 пакетов под ASan/UBSan; сквозной прогон
  fake_server --stage5 ↔ w3dlogin --walk со строгой проверкой пакетов движения). Реальные данные — через

Протокол, этапы 5.12–5.18 (stage5s, всё по vMaNGOS):
- Репутация: SMSG_INITIALIZE_FACTIONS (0x122) = u32 64 × {u8 flags, i32 standing}; standing — **приращение к базе** из
  Faction.dbc (база и флаги по маскам расы/класса, FactionEntry::GetIndexFitTo), ранг = ReputationToRank(база + standing);
  SET_FACTION_STANDING 0x124 (u32 n × {u32 index, i32}), SET_FORCED_REACTIONS 0x2A5, SET_FACTION_ATWAR 0x313.
  Реакция «мы → он» для фракции с репутацией — только Hostile (война) или Friendly; «он → мы» — ранг (война → не выше
  Neutral). Цвет имени — худшее из двух; атака — IsValidAttackTarget (нейтральные с репутацией — только при войне).
- Квест-лог в полях: PLAYER_QUEST_LOG_1_1 = 198 + 3·слот: id; счётчики по 6 бит на цель-существо + состояние в байте 3
  (1 выполнен, 2 провален); таймер. Предметные цели считает клиент по сумкам. SMSG_QUESTUPDATE_ADD_ITEM приходит
  **раньше** самого предмета (обновление объекта в конце тика) — строку «x/y» ждём по сумкам.
- Иконки квестов в gossip — DialogStatus (3 не выполнен, 4 можно сдать, 5 доступен); клиент решает по своему журналу:
  квест в журнале → CMSG_QUESTGIVER_COMPLETE_QUEST, иначе QUERY_QUEST. Сервер сам перескакивает с REQUEST_ITEMS на
  OFFER_REWARD, если ничего не нужно. QUEST_QUERY_RESPONSE 1.12 содержит «деньги на макс. уровне» (> 1.9.4).
- Торговец: слоты LIST_INVENTORY — только видимые строки, с 1; BUY_ITEM count = число «пачек» BuyCount; SELL_ITEM count 0 =
  вся стопка, успех без ответа (видно по сумкам и деньгам); выкуп — слоты 69..80, поля 0x270 (GUID) и 0x4CA (цены).
- Тренер: в списке — **обучающие** заклинания (эффект 36, EffectTriggerSpell); имя берём от того, чему учит
  (конвертер пишет такие строки в spells.txt). Каждая запись 38 байт + приветствие.
- Ауры: UNIT_FIELD_AURA 47 (48 слотов: 0–31 бафы, 32–47 дебафы), AURAFLAGS 95 (4 бита на слот, 1 = можно снять),
  AURAAPPLICATIONS 113 (байт = стаки − 1); время — только у своих (SMSG_UPDATE_AURA_DURATION 0x137 может прийти раньше поля).
- Группа: GROUP_LIST 1.12 с байтом сложности (> 1.10.2); PARTY_MEMBER_STATS — packed GUID + u32 маска (поля по битам).
- Объекты: GAMEOBJECT_TYPE_ID 21, DYN_FLAGS 19 (1 = можно использовать для нашего квеста), CMSG_GAMEOBJ_USE 0x0B1.
- **Исправлено: SMSG_ITEM_QUERY_SINGLE_RESPONSE** — между описанием и MaxDurability 10 полей (PageText..ItemSet), а не 11:
  прочность читалась из поля Area (на реальном сервере всегда 0). Fake-сервер повторял ту же ошибку — тоже исправлен.
  Теперь читаются StartQuest (предмет начинает квест → Use) и LockID; ITEM_FLAG_LOOTABLE 0x4 → кнопка Open (CMSG_OPEN_ITEM 0x0AC).

## Отложенные проблемы

1. **Швы/пустоты между LOD земли у ближних тайлов** (юбки не закрывают все случаи; вероятно, стык тайлов
   с разным LOD и порог 40/140 ярдов; нужна проверка порядка рёбер/глубины юбок или стыковка по соседям).
2. Проседание FPS на дальности 533–800 — ещё один уровень упрощения для дальних тайлов (Этап 6).
3. WMO: порталов нет (интерьеры рисуются всегда), MOCV не используется. Полы и стены есть (COLL, stage5e), но на
   реальных данных не проверены: размер COLL в лесу (стволы деревьев) и город (время `walls` в HUD) — смотреть первым.
   Потолков нет (прыжок под низкой крышей проходит сквозь неё); существа/игроки не сталкиваются.
4. Вода из MCLQ в регионе пользователя не найдена — проверить по region.png (парсинг MCLQ у WoWee есть).
5. TCP connect на 3DS блокирующий (на недоступном сервере интерфейс замирает до таймаута). В stage5s сознательно не
   трогали: неблокирующий connect + poll в libctru без консоли не проверить, а ошибка сломала бы вход совсем.
6. Warden — только по желанию и только где администрация не против (путь: ответы из образа WoW.exe + .cr-файлы, без эмулятора).
7. Old 3DS не проверялся.

## Сессия 4, часть 5 — полёты на грифонах и корабли (P1-10; на консоли НЕ проверено, и с настоящим сервером тоже)

Всё проверено только на PC (синтетические данные, ASan/UBSan, ARM11-компиляция). Реальных данных клиента и сервера здесь нет.

**Полёты (taxi).** Сервер сажает игрока на маунта (UNIT_FIELD_MOUNTDISPLAYID), ставит UNIT_FLAGS 0x4 | 0x00100000
(TAXI_FLIGHT) и шлёт SMSG_MONSTER_MOVE со сплайн-флагом Flying (0x200) — путь Catmull-Rom со скоростью 32 yd/s.
- `net/spline.hpp`: Catmull-Rom как в vMaNGOS (`Movement/spline/spline.cpp`: матрица, первая виртуальная точка 2·c0−c1, последняя
  повторена, длина сегмента по 3 шагам). `WorldObject::pathSmooth`, `positionAt` идёт по сплайну (время сегмента ∝ длине).
- `taxiFlight()`; в `main.cpp` режим полёта: позиция и курс — по сплайну сервера, наши пакеты движения не шлются
  (`mover.stopAll` на входе), камера за грифоном (≥ 9 yd, вращается стиком), на посадке — на землю и `mover.reset`.
- Анимация: `W3D_ANIM_FLY = 135` (в списке сохраняемых анимаций конвертера — НУЖНО пересобрать пак с creatures/players), грифон
  летит анимацией Fly (запасные Run, Walk, Stand), всадник сидит (Mount) — `CreatureSeen::flying`.
- Тест: `net/tests/spline_test.cpp` (непрерывность, прохождение узлов, линейный режим).

**Корабли и цеппелины (MO_TRANSPORT, GO type 15).** Сервер симулирует их по TaxiPathNode.dbc, клиенту шлёт только позицию
создания и прогресс пути (UPDATEFLAG_TRANSPORT, u32) — 1.12-клиент анимирует сам. Поэтому симуляция портирована:
- `net/transport.{hpp,cpp}`: `TransportPath::build` = `TransportMgr::GenerateWaypoints` (ключевые кадры, остановки actionFlag==2
  с delay, телепорт-кадры, расстояния «с остановки / до остановки», разгон/торможение по speed=data1 и accel=data2 шаблона GO),
  `at(progressMs)` = `ShipTransport::Update` + `CalculateSegmentPos` (позиция, курс = направление + π, `moving`). `TransportTable`
  читает `transports.txt`. Известное расхождение: сервер может подменять период из таблицы `transports` в БД — клиент считает
  по алгоритму, поэтому возможен дрейф относительно сервера (перезаход/повторное создание объекта пересинхронизирует).
- `ObjectTable::tickTransports` (раз в кадр, до всего остального): позиция каждого корабля = путь(прогресс при создании + время с
  приёма); пассажиры (MoveFlag OnTransport, смещение в пакете) переносятся: `mv` = поза корабля ⊕ смещение (поворот на угол
  корабля, как `CalculatePassengerPosition`), `WorldObject::carried` отключает экстраполяцию; ходьба по палубе между пакетами
  экстраполируется в локальных координатах. Всё остальное (метки, имена, звук) видит уже мировую позицию.
- Конвертер `--transports` (`--transport-filter ключи`, по умолчанию `transport,zeppelin,ship,boat` в пути модели
  GameObjectDisplayInfo): модели → CMDL, дисплей `CDSP` под id `0x80000000 | GameObjectDisplayInfo.ID` (формат пака не менялся);

## Part 13 — Dungeons and the portal effect (stage 5.24)

- Converter: `dungeon.cpp`. Instance maps have no ADTs, only a WDT with MPHD flag 0x01 and one global WMO (MWMO + MODF).
  `convertDungeon` places that building with `placeWmo`, splits the group placements by tile (centre of the group), and every tile
  that has placements or collision gets a TERR that is a single quad 300 yd below the lowest floor (the client loads a tile only
  when it has a TERR), a PLCM and the COLL (the region clip is lifted to 0..63). The tile at (0,0) is always added.
  `w3dconv --dungeons -o <folder>` reads Map.dbc and writes `map<ID>.w3dp` for every WDT-only map; `--map <dir>` of such a map
  converts it through the normal path. GUI: checkbox "Dungeons and raids" (separate step, same creature/player options: each pack
  carries its own copies of the models, so this is big). Test: `converter/tests/run_dungeon_tests.sh`.
- Client: `portal.cpp` (PortalFx, flat HudList quads: swirl of spiral arms, disc, sparks; tested by `tests/portal_test.cpp`).
  SMSG_TRANSFER_PENDING (`takeTransferPending`) starts it over the old world; at SMSG_NEW_WORLD the portal is closed over the old
  world, the pack is swapped under it (wait loop draws the swirl on both screens and now waits for the tile AND its collision,
  a dungeon floor is only collision), then it opens over the new world. 25 s without a new map opens it again.
- Not verified on a console or a real server. The original client has no portal here (it shows a loading screen); the swirl is our own.

## Part 14 — Loading screens and real loading (stage 5.25)

- The swirl was our own invention; the game shows the map's loading screen. `w3dconv --ui` now reads Map.dbc + LoadingScreens.dbc and
  puts one 512x256 ETC1 picture per map into ui.w3dp (`W3dUiLoading`, in the former reserved fields of W3dUiDir, so old packs
  still open). The Map.dbc column of the loading screen id is found by itself (all values are LoadingScreens ids, most distinct
  values); the log line "loading screens: N maps (Map.dbc column C)" tells which one it took. Square pictures are cropped to
  their top 3/4 (4:3 picture in a square texture) - a guess that has to be looked at on real data.
- Client: PortalFx shows the picture + progress bar (the swirl only when the pack has no picture). Entering the world and every
  teleport whose destination tile/collision is not ready start `loadingWorld`: the character is frozen (no gravity, no steps, no
  jump) until the tile AND its collision under it are ready (and no tile is still loading, or 3 s passed; 25 s at most), so nobody
  falls through floors that are not streamed yet. The network keeps running meanwhile (this wait is in the main loop; only
  the pack swap itself blocks).
- Tests: run_dungeon_tests.sh (ui.w3dp with 6 loading screens), tests/loading_pack_test.cpp, tests/portal_test.cpp.

## Part 20 — Подгрузка без провалов: постепенный показ и очередь чтения по приоритету (этап 5.30; на консоли НЕ проверено)

Причина провалов (report.txt пользователя: тайл до показа в среднем 3,1 с, максимум 12,9 с; памяти хватает — 48 из ~124 МБ,
белых текстур 0): тайл рисовался только когда готово ВСЁ его содержимое (рельеф, каждая модель, каждая текстура), а чтения
шли одной очередью по порядку запросов.

Клиент (`streamer.cpp`, `render.cpp`, `main.cpp`):
- Постепенный показ: тайл становится Ready, когда прочитан рельеф и его текстуры (рисуется земля); вода — когда её текстуры
  (`Tile::waterReady`); каждая модель — когда она и её текстуры готовы (`Model::drawable`, список `g_waitingModels`);
  радиус экземпляра заполняет рендер при первом показе. `Tile::complete` — всё содержимое тайла на месте (статистика).
- Очередь чтения с приоритетом: у каждого чтения — точка, где оно нужно (центр тайла, позиция размещения; текстуры модели —
  от модели, текстуры рельефа — от тайла) и класс (существа/игроки/предметы/сцены экранов — сразу; рельеф/размещения тайла;
  коллизия; текстуры рельефа; модели; текстуры зданий; текстуры мелочей). Каждый кадр очередь сортируется: расстояние от
  камеры × класс × «позади камеры» (×1,35/×1,8), полосами, расширяющимися с расстоянием (96 ярдов, дальше ×2,5) — внутри
  полосы по порядку в файле (SD читает подряд намного быстрее). Чтения, которые уже никому не нужны (тайл отпущен, модель/
  текстура освобождена), отбрасываются, не читаясь. Новые чтения сразу уходят простаивающему потоку.
- Загрузки текстур в видеопамять — ближние первыми; бюджет 2,5 мс/кадр, 5 мс если ждут больше 24, 14 мс под экраном загрузки

## Part 25 — Анимация костей моделей эффектов (этап 5.35; на консоли НЕ проверено)

- Модели эффектов заклинаний вращаются, пульсируют и качаются (кольцо, щит, аура). Конвертер (`model.cpp`, только для
  эффектов заклинаний, `--spell-fx`) запекает первую зацикленную анимацию модели (Stand; иначе первую, при пустой — самую

  блоба) едет жёстко на своей главной кости (по весам вершин), излучатели и свечения — на кости излучателя / карточки.

  (`animOff4`, 0 = нет; старый клиент его не читает). `w3d_fx_anim()` проверяет границы, `w3d_fx_anim_matrix()` берёт
  матрицу кости на возрасте эффекта (смесь двух ближайших кадров, цикл замкнут).
- Клиент: `Model::fxAnim` (streamer), возраст эффекта идёт от режиссёра (`Placed.ageMs` -> `SceneModel.fxAgeMs` ->
  `Instance.animMs` / `fx::Source.animMs`). `drawModels` домножает матрицу кости на `mv` каждой части; `fx.cpp` двигает точку
  рождения частиц и направление выброса (излучатель на вращающейся кости) и центры свечений. Сфера видимости эффекта
  увеличена в 1,5 раза (части уходят от центра).
- `--info`: «effects: N models, ..., K with bone animation», проверка блока (число частей/излучателей/свечений, кости, конечность
  матриц). Тесты: `fx_test` (блок, валидация, цикл), `gen_spellfx_data.py` (щит с кольцом на кости, вращение 1 об/с),

### 5.35b — «Всё сразу» не заканчивался

Причина: после записи всех файлов `--all` проверяет каждый пак карты (`printPackInfo`), а пак читался в память побайтно
(`istreambuf_iterator`) — на паках в гигабайты это минуты на карту, с десятками карт процесс казался зависшим (GUI ждёт конца
вывода процесса). Теперь файл читается одним блоком (`readFileFast`; то же в `w3dpreview`), перед проверкой печатается
«== checking the packs» и «checking <файл> ...» для каждой карты, чтобы было видно, что идёт проверка.

### 5.35g — эффекты заклинаний на настоящих данных (по explain.txt пользователя)

Три причины, по которым в пуле было 16 заклинаний и 2 модели эффектов (а «Огненного шара» не было вовсе):
1. **Модели из одних частиц отбрасывались.** Большинство эффектов 1.12 — 0 вершин, только излучатели (Fire_Precast_Hand,
   Fire_Cast_Hand, MoltenBlast_Impact_Chest, LesserHeal_Base, Immolate_*, Shadow_Precast_Low_Hand, LootFX ...):
   `addModelFromGame` считал их битыми. Теперь (эффекты включены) такая модель — один вырожденный треугольник с излучателями;
   лог «N models of particles only».
2. **Столбцы SpellVisual 1.12**: 6 — флаг «есть снаряд» (0/1), 7 — модель снаряда (читался 8 — тип траектории), канального
   комплекта нет (флаг в 6 читался как комплект). Столбец снаряда выбирается из 7 / 8 по данным, канальный — только если
   в столбце действительно разные комплекты; иначе канал показывает комплект подготовки (и считается каналом: подготовка
   гасла бы от событий самого заклинания).
3. **Пустые ячейки SpellVisualKit — -1** (0xFFFFFFFF), не 0: проверка столбцов 5.35c считала их «не эффектами» и
   отключила все столбцы комплектов.
Синтетика переведена на раскладку 1.12 (флаг 6, снаряд 7, -1 в пустых ячейках, эффект из одних частиц).

### 5.35h — конвертер: окно, «не заканчивается», скорость

- **«Не заканчивается» (настоящая причина):** окно получало каждую строку вывода отдельным сообщением Windows (PostMessage).
  У очереди сообщений потока предел 10 000; «Всё сразу» печатает ~40 000 строк, а в конце (проверка паков) — лавиной:
  очередь переполнялась, и последнее сообщение «готово» терялось — окно висело в «работе», хотя w3dconv уже вышел.
  Теперь вывод идёт в общий буфер (последние 600 строк), окно берёт его по таймеру (250 мс); конец шага — по завершению
  процесса (PeekNamedPipe + WaitForSingleObject), даже если трубу держит кто-то ещё.
- **Окно заново (англ.):** Folders → What to convert (Everything (recommended) / Selected parts only: карта, участок
  тайлов, подземелья) → Content (интерфейс, звук, броня; существа / игроки / корабли — всегда в Everything) → Options
  (качество текстур, доп. параметры) → Start / Cancel / Open the output folder, прогресс, строка шага с прошедшим
  временем, «Now: …» — текущий раздел вывода («== map 1 (Kalimdor) …»), лог моноширинным шрифтом. Первый запуск — Everything.
- **Скорость:** текстуры (кодирование ETC1 / 16 бит с мипами — основная часть времени) кодируются пулом потоков (ядра − 1),
  пока основной поток собирает модели, здания и тайлы; BLP читается и декодируется в основном потоке (MPQ не
  потокобезопасен). Готовые текстуры добавляются в пак основным потоком; запись пака и его уничтожение сначала ждут все.
  `W3D_THREADS=1` — по-старому. Лог «Всё сразу»: время каждой карты и строка «timing: …» в конце.
